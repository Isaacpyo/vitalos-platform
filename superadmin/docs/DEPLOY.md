# Deploying the Vitalos Super Admin

Target: **https://admin.vitalos.co.uk** on Azure Container Apps (UK South), with Azure Database for PostgreSQL 17, Azure Key Vault and a managed TLS certificate. DNS stays in Cloudflare (ADR-007).

## Status (10 Oct 2026)

**Not live yet. The one remaining step is to run the deploy with Vitalos credentials (section 2).**

The session that built this app had no Azure, Fly.io, Railway or Render CLI or MCP connection, and no Cloudflare access. It did not use any cloud credentials that are not Vitalos's. Everything else is done and has been verified:

| Verified                                                                                              | How                                                                                          |
| ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Production image builds (multi-stage, non-root, WhiteNoise, gunicorn)                                 | `docker build`, locally and in CI                                                            |
| Release job: migrate, `seed_architecture`, `create_superadmin`. Idempotent                            | Run twice against a fresh PostgreSQL, locally and in CI                                      |
| Full browser smoke test against the production image (prod settings, PostgreSQL, TOTP)               | `e2e/smoke.py`: 25/25 checks, locally and in CI. Screenshots in `docs/screenshots/`          |
| Backup job writes a restorable dump and prunes copies older than 14 days                              | `bin/backup.sh`, then `pg_restore` into a scratch database                                   |
| Deploy script syntax and Azure CLI flags                                                              | `bash -n`, `shellcheck`, and every flag checked against `az` 2.91 `--help`                   |

The deploy script has **not** been run against a real subscription. Expect to read its output on the first run. It is idempotent, so you can fix the cause of any failure and re-run it.

## 1. What gets created

All resources go in resource group `rg-vitalos-superadmin-prod`, region `uksouth`. The globally unique names derive from `AZ_NAME_PREFIX` (default `vitalossa`). If a name is already taken, change the prefix.

| Resource                       | Name (default)                                 | Notes                                                                                     |
| ------------------------------ | ---------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Key Vault (RBAC)               | `kv-vitalossa`                                 | The secrets manager. Purge protection on                                                  |
| User-assigned managed identity | `id-vitalossa`                                 | Pulls images (AcrPull) and reads secrets (Key Vault Secrets User)                         |
| PostgreSQL Flexible Server 17  | `psql-vitalossa`, database `superadmin`        | Burstable B1ms, 32 GB, **managed backups kept 14 days**, TLS required                     |
| Container Registry (Basic)     | `vitalossaacr`                                 | Image `superadmin:<git sha>`. Admin user disabled                                         |
| Log Analytics workspace        | `log-vitalossa`                                | Container logs, 30-day retention                                                          |
| Container Apps environment     | `cae-vitalossa`                                |                                                                                           |
| Container app                  | `superadmin`                                   | External ingress on port 8000, 1–3 replicas, 0.5 vCPU / 1 GiB                             |
| Job (manual trigger)           | `superadmin-release`                           | `bin/release.sh`: migrate, seed, bootstrap admin                                          |
| Job (scheduled, 02:15 UTC)     | `superadmin-backup`                            | `bin/backup.sh`: `pg_dump` to Azure Files, 14 daily copies                                |
| Storage account + file share   | `stvitalossabackup` / `backups`                | Target for the nightly dumps                                                              |
| DNS (Cloudflare)               | `admin` CNAME, `asuid.admin` TXT               | DNS only (not proxied). Managed certificate bound by Container Apps                       |

### Secrets and environment variables

Secrets are generated by the script, stored only in Key Vault, and given to the containers as Key Vault references. They are never printed or committed.

| Key Vault secret           | Container env var          | Used by                   |
| -------------------------- | -------------------------- | ------------------------- |
| `django-secret-key`        | `DJANGO_SECRET_KEY`        | app, release job          |
| `database-url`             | `DATABASE_URL`             | app, release, backup jobs |
| `bootstrap-admin-password` | `BOOTSTRAP_ADMIN_PASSWORD` | release job only          |
| `postgres-admin-password`  | (none; inside `database-url`) | PostgreSQL admin       |
| `sentry-dsn` (optional)    | `SENTRY_DSN`               | app                       |

Plain environment variables: `DJANGO_SETTINGS_MODULE=config.settings.prod`, `ALLOWED_HOSTS=admin.vitalos.co.uk`, `CSRF_TRUSTED_ORIGINS=https://admin.vitalos.co.uk`, `SECURE_SSL_REDIRECT=True`, `TRUSTED_PROXY_COUNT=1`, `APP_ENVIRONMENT=production`, `LOG_FORMAT=json`, and, on the release job, `BOOTSTRAP_ADMIN_EMAIL=superadmin-owner@example.invalid`. See `.env.example` for every supported key.

**The bootstrap admin password is in Key Vault `kv-vitalossa`, secret `bootstrap-admin-password`** (container env var `BOOTSTRAP_ADMIN_PASSWORD`). Only the founder should retrieve it, and only to sign in for the first time:

```sh
az keyvault secret show --vault-name kv-vitalossa --name bootstrap-admin-password --query value -o tsv
```

## 2. Deploy (the remaining step)

### 2.0 One-time checks (founder, about 10 minutes)

```sh
# Who is authoritative for vitalos.co.uk? stage-status.md says Cloudflare activation was pending.
dig +short NS vitalos.co.uk
```

If the nameservers are not `*.ns.cloudflare.com`, create the two DNS records from section 2.3 at the current DNS host instead, and leave `CLOUDFLARE_API_TOKEN` unset.

Cloudflare API token: in the Cloudflare dashboard, open **My Profile → API Tokens → Create Token → Edit zone DNS**. Set **Zone Resources** to **Include → Specific zone → vitalos.co.uk**.

### 2.1 Option A, recommended: GitHub Actions, one click

This needs no long-lived Azure keys (OIDC federation), and every run is auditable. Run this once as a subscription Owner, for example in Azure Cloud Shell:

```sh
SUB=<vitalos-subscription-id>
az account set --subscription "$SUB"
for p in Microsoft.App Microsoft.OperationalInsights Microsoft.ContainerRegistry Microsoft.DBforPostgreSQL \
         Microsoft.KeyVault Microsoft.Storage Microsoft.ManagedIdentity; do az provider register -n "$p" --wait; done
az group create -n rg-vitalos-superadmin-prod -l uksouth --tags app=vitalos-superadmin env=production

APP_ID=$(az ad app create --display-name github-vitalos-superadmin-deploy --query appId -o tsv)
SP_OBJECT_ID=$(az ad sp create --id "$APP_ID" --query id -o tsv)
az ad app federated-credential create --id "$APP_ID" --parameters '{
  "name": "github-production-environment",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:Isaacpyo/vitalos-platform:environment:production",
  "audiences": ["api://AzureADTokenExchange"]}'
# Owner on the resource group only: it can create resources and the app's role assignments there.
az role assignment create --assignee-object-id "$SP_OBJECT_ID" --assignee-principal-type ServicePrincipal \
  --role Owner --scope "$(az group show -n rg-vitalos-superadmin-prod --query id -o tsv)"
echo "AZURE_CLIENT_ID=$APP_ID  AZURE_TENANT_ID=$(az account show --query tenantId -o tsv)  AZURE_SUBSCRIPTION_ID=$SUB  AZURE_DEPLOYER_OBJECT_ID=$SP_OBJECT_ID"
```

None of the four printed values is secret.

In GitHub, open **Settings → Environments → New environment `production`**. Add yourself as a **required reviewer**, then add:

- Secrets: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `CLOUDFLARE_API_TOKEN`, and optionally `SENTRY_DSN`.
- Variable: `AZURE_DEPLOYER_OBJECT_ID`.

Merge the PR, then open **Actions → Super Admin deploy → Run workflow** on `main`. Type `DEPLOY`, and tick **smoke test** on this first run only. Approve the environment gate.

The workflow provisions everything, deploys and waits for valid HTTPS. It then runs `e2e/smoke.py` against the live URL and uploads screenshots as an artifact. Copy those screenshots into `superadmin/docs/screenshots/live/`.

Run the live smoke test **before** your own first sign-in. It enrols a temporary authenticator on the bootstrap account and removes it at the end, so that your first sign-in enrols your own. Once a real authenticator exists, the smoke step reports *skipped* rather than failing. Screenshot artifacts are kept for 7 days. Leave **smoke test** unticked for later deploys, so that screenshots of real (possibly Confidential) data are never captured.

### 2.2 Option B: run the script yourself

You need: bash, Azure CLI 2.70 or later (`az login` as an Owner), Docker with BuildKit, python3, curl and a checkout of this repo.

```sh
az login
az account set --subscription <vitalos-subscription-id>
# One-time provider registration and resource group: the first four lines of 2.1.
export AZ_SUBSCRIPTION=<vitalos-subscription-id>
export CLOUDFLARE_API_TOKEN=<token from 2.0>   # optional; omit to create DNS by hand
# export SENTRY_DSN=...                         # optional
superadmin/deploy/azure/deploy.sh
```

Optional overrides: `AZ_NAME_PREFIX`, `AZ_RESOURCE_GROUP`, `AZ_LOCATION`, `CUSTOM_DOMAIN`, `BOOTSTRAP_ADMIN_EMAIL` and `IMAGE_TAG`.

### 2.3 What the script does, in order (the manual equivalent)

1. Registers providers if needed and creates the resource group and Key Vault. Generates the missing secrets with Python's `secrets` module, writing them to mode-0600 temp files and passing them to Key Vault with `--file`.
2. Creates the managed identity and grants it **Key Vault Secrets User** and **AcrPull**.
3. Creates `az postgres flexible-server create --version 17 --tier Burstable --sku-name Standard_B1ms --storage-size 32 --backup-retention 14 --public-access 0.0.0.0` (Azure services only), then the `superadmin` database. It stores `database-url` as `postgres://vitalosadmin:…@psql-vitalossa.postgres.database.azure.com:5432/superadmin?sslmode=require`.
4. Builds and pushes the image with `docker buildx build --platform linux/amd64 --push`, tagged `<registry>/superadmin:<git sha>`.
5. Creates Log Analytics and the Container Apps environment.
6. Creates and runs the **release job** `/app/bin/release.sh` and waits for `Succeeded`. Migrations always run before the new code takes traffic. `create_superadmin` only creates the bootstrap account if it is missing. It never re-activates, re-promotes or changes an existing account, so a deliberate deactivation survives redeploys.
7. Creates or updates the **container app** with the new image.
8. Creates the storage account and `backups` share, mounts it in the environment and creates the **backup job** from `deploy/azure/backup-job.yaml`.
9. Writes the DNS records. If a record with the same name already points somewhere else, the script stops rather than overwrite it; check what uses that record, then re-run with `DNS_OVERWRITE=1`. Without a Cloudflare token it prints the records and exits; create them, then re-run:

   | Type  | Name          | Value                                                                           |
   | ----- | ------------- | ------------------------------------------------------------------------------- |
   | CNAME | `admin`       | the app FQDN, e.g. `superadmin.<hash>.uksouth.azurecontainerapps.io`            |
   | TXT   | `asuid.admin` | the app's `customDomainVerificationId`                                          |

   Both must be **DNS only (grey cloud)**, with TTL 300.

10. Waits for the records to resolve (DNS-over-HTTPS). Runs `az containerapp hostname add` and `az containerapp hostname bind --validation-method CNAME`, which issues a free managed certificate. Then waits for `https://admin.vitalos.co.uk/healthz/` to succeed with a valid certificate.

## 3. Verify

```sh
curl -sS https://admin.vitalos.co.uk/healthz/                  # {"status": "ok"}
curl -sSI https://admin.vitalos.co.uk/login/ | grep -iE 'HTTP/|strict-transport|content-security'
curl -sSI http://admin.vitalos.co.uk/ | head -1                 # redirect to https

# Full browser check (also produces screenshots). Run before the owner's first sign-in; see 2.1.
cd superadmin && pip install -r requirements.txt -r requirements-dev.txt && python -m playwright install chromium
SMOKE_BASE_URL=https://admin.vitalos.co.uk SMOKE_EMAIL=superadmin-owner@example.invalid \
SMOKE_PASSWORD="$(az keyvault secret show --vault-name kv-vitalossa --name bootstrap-admin-password --query value -o tsv)" \
python e2e/smoke.py --screenshots docs/screenshots/live
```

The smoke test signs in and enrols TOTP. It opens all six dashboards and every tab, then creates and edits a Practice → Solution → Offer, a Project (with an inline status change) and a KPI value (a target breach). It checks live search, the activity feed and the Django-admin history rows, and confirms there are no CSP violations. It then archives its records (all named "Smoke test …"; history is kept) and removes its temporary authenticator.

### First sign-in (founder)

1. Retrieve the password (section 1) and open https://admin.vitalos.co.uk.
2. Sign in with `superadmin-owner@example.invalid`. You will be asked to scan a QR code with Microsoft Authenticator or 1Password, because TOTP is mandatory for SuperAdmin.
3. Go to **Account & security → Change password**, and set a new password (12 characters or more).
4. Add users under **Settings → Users & roles**, and assign line owners by editing each service line.

## 4. Redeploy

Run the workflow again, or run `deploy.sh` again from the commit you want. The script reuses every resource. It builds `superadmin:<sha>`, runs the release job (migrations) and then switches the app to the new image. Revisions run in single mode, and the new revision receives traffic once it starts.

Image-only redeploy, by hand:

```sh
TAG=$(git rev-parse --short=12 HEAD); IMAGE=vitalossaacr.azurecr.io/superadmin:$TAG
az acr login -n vitalossaacr && docker buildx build --platform linux/amd64 -t "$IMAGE" --push superadmin
az containerapp job update -n superadmin-release -g rg-vitalos-superadmin-prod --image "$IMAGE"
az containerapp job start -n superadmin-release -g rg-vitalos-superadmin-prod   # wait: az containerapp job execution list ...
az containerapp update -n superadmin -g rg-vitalos-superadmin-prod --image "$IMAGE"
az containerapp job update -n superadmin-backup -g rg-vitalos-superadmin-prod --image "$IMAGE"
```

## 5. Roll back

Application code:

```sh
az containerapp revision list -n superadmin -g rg-vitalos-superadmin-prod -o table          # find the last good image
az containerapp update -n superadmin -g rg-vitalos-superadmin-prod --image vitalossaacr.azurecr.io/superadmin:<previous sha>
```

Migrations only move forward. Before rolling back across a migration, check that the previous code tolerates the newer schema. Migrations in this project are additive. If a migration itself must be undone, restore the database (section 6) to a point before the release. Never drop tables by hand.

Remove the public endpoint quickly, without deleting anything:

```sh
az containerapp ingress disable -n superadmin -g rg-vitalos-superadmin-prod
```

DNS: delete or repoint the `admin` CNAME in Cloudflare. No other Vitalos records are touched by this deployment.

## 6. Backups and restore

- **Managed (primary):** Azure PostgreSQL automated backups, kept 14 days, with point-in-time restore to any second in that window.
- **Logical (secondary):** the nightly `superadmin-backup` job writes `superadmin-<UTC timestamp>.dump` (`pg_dump -Fc`) to the `backups` Azure Files share, keeps 14 daily copies and verifies each archive with `pg_restore --list`.

Point-in-time restore. This creates a **new** server, so the original stays untouched:

```sh
az postgres flexible-server restore -g rg-vitalos-superadmin-prod --name psql-vitalossa-restore \
  --source-server psql-vitalossa --restore-time "2026-10-20T09:00:00Z"
# Inspect it, then point the app at it by updating the Key Vault secret (same password as the source):
#   database-url -> postgres://vitalosadmin:<password>@psql-vitalossa-restore.postgres.database.azure.com:5432/superadmin?sslmode=require
az containerapp revision restart -n superadmin -g rg-vitalos-superadmin-prod \
  --revision "$(az containerapp revision list -n superadmin -g rg-vitalos-superadmin-prod --query '[0].name' -o tsv)"
```

Restore a nightly dump. Use the app image, whose client is version 17, into an **empty** database:

```sh
az storage file download --account-name stvitalossabackup --share-name backups \
  --path superadmin-<timestamp>.dump --dest ./restore.dump --auth-mode key
docker run --rm -v "$PWD:/restore:ro" vitalossaacr.azurecr.io/superadmin:<sha> \
  pg_restore --no-owner --no-privileges --dbname "<target database url>" /restore/restore.dump
```

## 7. Operations

```sh
az containerapp logs show -n superadmin -g rg-vitalos-superadmin-prod --follow     # JSON lines with request_id
az containerapp job execution list -n superadmin-backup -g rg-vitalos-superadmin-prod -o table
```

Every response carries `X-Request-ID`; search for it in Log Analytics (`ContainerAppConsoleLogs_CL`). Set `SENTRY_DSN` (in Key Vault, then redeploy) to report errors. Personal data is not sent.

To rotate the Django secret key, update the Key Vault secret `django-secret-key` and restart the revision. This signs everyone out. Rotate the database password with `az postgres flexible-server update --admin-password`, then update `database-url` to match.

If someone forgets their password, a SuperAdmin cannot see it, because passwords are hashed. Use **Settings → Users & roles → Edit** to deactivate the account, then recreate it. Or a superuser can set a new password in `/django-admin/`.

If someone loses their authenticator, a superuser deletes their TOTP device in `/django-admin/` (**OTP_TOTP → TOTP devices**). They enrol again at next sign-in.

## 8. Local development

```sh
cd superadmin
uv venv --python 3.12 .venv && uv pip install -r requirements.txt -r requirements-dev.txt   # or python -m venv + pip
bin/tailwind.sh                          # builds static/css/app.css (downloads the pinned CLI once)
python manage.py migrate && python manage.py seed_architecture
BOOTSTRAP_ADMIN_PASSWORD='<12+ chars>' python manage.py create_superadmin --email you@vitalos.co.uk
python manage.py runserver               # http://localhost:8000
pytest                                   # SQLite; set DATABASE_URL to run on PostgreSQL like CI
```

With Docker, run `bin/tailwind.sh --watch` in one terminal and `docker compose up --build` in another. That runs PostgreSQL 17 with live code reload.
