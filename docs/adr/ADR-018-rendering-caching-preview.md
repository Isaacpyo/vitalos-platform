# ADR 018 Rendering, caching, preview and content-source selection

Status: Accepted.

## Context

Stage 1 serves content from Sanity (editorial) through a framework-free `ContentSource` (ADR-022) on Next.js 16.4. The platform must: build and run with no Sanity configuration; show published content fast and fresh after an edit; let editors preview drafts; keep drafts, tokens and the webhook secret away from visitors and client bundles; keep search engines out of every non-production environment; and answer legacy URLs correctly. Several parallel workstreams (templates, contact form, quality suites) build on this layer, so the choices below also had to be cheap for them.

## Decision

1. **Content source selection** (`apps/web/src/lib/cms/get-content-source.ts`). `VITALOS_CONTENT_SOURCE` (validated by `@vitalos/config`) selects `empty`, `sanity` or `fixtures`. The selection logic is a map of factories (`content-source-factory.ts`) with injected loaders, which is the extension point for new sources. `empty` is the honest empty state and is what builds and CI use without Sanity. `sanity` needs a project id and calls `createSanityContentSource(fetcher)` exported by `@vitalos/cms/queries` (workstream C2); if that export is missing it fails loudly, because silently serving an empty site when Sanity was requested would be dishonest. `fixtures` calls `createFixtureContentSource(set)` from `@vitalos/cms/fixtures` (C2) and falls back to the empty source with a warning until it exists; it is rejected in production. `getContentSource()` returns a draft-aware wrapper; `getPublishedContentSource()` is for the sitemap and static generation.

2. **Caching: tag-based ISR through the data cache, not Cache Components.** `src/lib/cms/fetch.ts` is the single seam. Published reads use `cache: "force-cache"` with `next.tags` (always the root tag `sanity`, plus caller tags) and a one-hour `revalidate` safety net; draft reads use `cache: "no-store"`. Pages stay statically generated (`generateStaticParams`) and are refreshed on demand.

   _Spike (Next.js 16.4.0, this repository):_ enabling `cacheComponents: true` with `partialPrefetching: true` builds the current routes, but it changes the rules for every route handler and page other workstreams are writing at the same time: route handlers such as `/api/health` become prerendered unless they read request data; every request-time read (`searchParams` on the contact page, `headers()`, `cookies()`, Draft Mode in the layout) must sit under `<Suspense>` or the build fails; the `dynamic`, `revalidate` and `fetchCache` segment options are not allowed; and `'use cache'` functions cannot take class instances or read `cookies()`/`headers()`. Adopting it now would force coordinated edits in `next.config.ts` (owned by W0), the contact form (H), the page templates (G2a/G2b) and the e2e harness (F1), for no visible benefit at this content volume (dozens of documents, edited rarely). Tag-based ISR gives the same on-demand freshness with the stable API and no cross-team change. The switch later is confined to `fetch.ts` (use a `'use cache'` function with `cacheTag(...tags)` and `cacheLife(...)`; Draft Mode `isEnabled` is readable inside cached scopes) plus the flag and Suspense work, and the tags and webhook stay as they are.

3. **Invalidation.** `POST /api/revalidate` receives the Sanity webhook. The signature (`sanity-webhook-signature: t=<ms>,v1=<base64url HMAC-SHA256 of "<t>.<body>">`) is verified with Node `crypto` and `timingSafeEqual` before the body is parsed, with a 64 KB body cap and a ten-minute replay window. `next-sanity/webhook`'s `parseBody` was not used because it compares signatures with `!==`, waits three seconds, and parses before verifying. No secret configured answers 503 (fail closed); a bad or missing signature answers 401; nothing is echoed back. A valid request calls `revalidateTag(tag, { expire: 0 })` for the root tag, `sanity:<type>` and `sanity:<type>:<slug>` (identifiers only), so the next request reads fresh content (an editor who just published sees it, rather than one stale view). Webhook configuration in Sanity is an owner-approved later step (projection `{ _type, "slug": slug.current }`).

4. **Draft Mode.** `GET /api/draft-mode/enable` is `next-sanity`'s `defineEnableDraftMode`, which validates the short-lived `sanity-preview-secret` stored in the dataset (read with the read token) and sets the bypass cookie; a missing or wrong secret answers 401, and a missing project id or read token answers 503 without enabling anything. `/api/draft-mode/disable` (POST, and GET for Presentation) clears the cookie and redirects only to same-site paths. With Draft Mode on, `getContentSource()` reads the `drafts` perspective with `SANITY_API_READ_TOKEN` and never caches; explicit `preview: true` cannot force draft reads without Draft Mode, and a read token is required. `DraftIndicator` (a banner in page flow with a POST exit form) and `VisualEditing` mount in the root layout only while Draft Mode is on, so visitors receive neither. The token is read only by server modules (`client.ts`, `draft-mode.ts` routes) and is checked for in client bundles by `check:bundle-secrets`. Stega encoding stays off so mappers work on plain strings; the Presentation overlay therefore relies on navigation and refresh, and enabling stega is a later option. In production the CSP (ADR-020) does not allow Sanity API connections from the browser, so overlays only work outside production; server-side draft previews still work.

5. **Publication gates in pages** (`src/features/publication-gates`). `requireGateOpen(gate)` calls `notFound()` for a closed gated index (editors in Draft Mode may preview it); `isDetailIndexableNow(gate)` drives `noindex` for details of a closed section. Thresholds and decisions stay in `@vitalos/cms`; route-to-gate mapping is derived from the route manifest.

6. **SEO** (`src/features/seo`). `buildMetadata` produces canonical, Open Graph and Twitter metadata from document SEO, then document fields, then site defaults, and marks pages `noindex` when the document, a closed gate or a non-production environment says so. `metadataBase` is set in the root layout. JSON-LD builders are pure and emit only fields the content has: Organization and WebSite use the brand name and site URL when settings are empty; Article needs a named author and a date; ProfilePage uses only present fields and verified `sameAs`; JobPosting only for an open, unexpired role with a description and a location; BreadcrumbList needs two crumbs. `serializeJsonLd` escapes `<` and the line separators. `robots.txt` disallows everything unless the deploy env is production (and keeps `/api/` out in production, leaving `/_next/` crawlable); the sitemap is built from the published perspective, lists the home page and index pages only when their documents exist, only gate-open sections, and only clean paths from the route manifest. It does not depend on the environment, so gating can be tested against fixtures.

7. **Redirects** (`src/features/redirects`). A version-controlled map: the four specified redirects (`/services` to `/what-we-do`, `/technologies` to `/labs`, `/privacy` to `/legal/privacy`, `/terms` to `/legal/terms`) as 301s, plus `generated.ts`, written by the owner-run `tooling/scripts/redirects-pull.mjs` from published Sanity `redirect` documents (empty until the owner approves some). `next.config.ts` validates the whole map at build (exact paths only, unique sources, no chains, no loops, no blanket redirect to `/`, no redirect of a live route, same-site destinations) so an invalid map fails the build. `410` rules are answered by the proxy (`gone.ts`).

8. **Rich text, images, errors, fonts.** `RichText` renders normalised blocks (paragraphs, h2-h4 with h1 downgraded, lists, blockquote, callout, attributed pull quote, code, figure; https or same-site links only; unknown blocks dropped) as plain semantic HTML, to be mapped onto `@vitalos/ui` primitives later. `CmsImage` renders nothing unless the image is renderable and, when a rights status is present, approved; only Sanity CDN and same-origin URLs are accepted (matching the CSP), through a Sanity loader (no `remotePatterns` change). `not-found.tsx`, `error.tsx` and `global-error.tsx` show facts, never error messages, and the digest as a support reference. Geist Sans and Mono come from the installed `geist` package (self-hosted, provisional pending the owner's typography decision).

9. **Refinements after review.**
   - _Published reads bypass the Sanity CDN_ (`useCdn: false`). After a webhook revalidation the CDN could still return the previous version and the ISR cache would store that stale copy; reads are cached by Next.js, so the live API is hit once per tag refresh, not per visitor.
   - _Draft Mode exit:_ `POST /api/draft-mode/disable` answers **303** (the browser follows with a GET), `GET` answers 307; the `Location` is a relative same-site path. Caveat: when the site is framed cross-site by the Studio (Presentation), next-sanity sets the bypass cookie with the `Partitioned` attribute; `draftMode().disable()` clears the unpartitioned cookie, so exiting from inside the frame may not clear the partitioned copy until the frame is closed or the Studio's own "disable preview" action runs. Exiting from a top-level tab works as expected.
   - _Redirects reach the site through a pull, not automatically._ Publishing a `redirect` document in the Studio changes nothing live: the owner runs `tooling/scripts/redirects-pull.mjs`, reviews the `generated.ts` diff and redeploys. Destinations may be same-site paths or `https` URLs (as the Studio allows); external destinations skip the chain, loop and blanket checks. A redirect source may not be a static manifest page or an `/api` path, but a dynamic detail path (`/insights/old-slug`) may be redirected, so slug changes work (this mirrors `shadowsLiveRoute` in the Studio rules).
   - _Webhook body handling:_ requests without a well-formed signature header are refused before any body is read, and the body is read as a stream that stops at 64 KB, so a chunked body without `Content-Length` is never buffered unbounded.
   - _Typography:_ only Geist Sans and Mono are loaded (`.variable` classes on `<html>`; the token stack applies). Source Serif 4 is not loaded: `next/font/google` downloads at build time, which is deferred until the owner confirms the typeface.
   - _UI and links:_ error pages, the draft banner and `RichText` use `@vitalos/ui` primitives (`Section`, `Container`, `Heading`, `Lead`, `Button`, `Prose`, `Callout`, `Quote`). Rich-text links and redirect targets reuse `isSafeRelativeRedirect`; `CmsImage` and Open Graph images are limited to this project's `/images/<projectId>/` path when `NEXT_PUBLIC_SANITY_PROJECT_ID` is set.

## Options

- Cache Components now: rejected for the reasons in decision 2; revisit below.
- `unstable_cache` around the Sanity client: rejected, the client already supports `next.tags` on `fetch` and `unstable_cache` is slated to be replaced by `'use cache'`.
- `next-sanity`'s `sanityFetch`/`SanityLive` (live content API): rejected for now, it needs Cache Components or live-subscription client code, and the webhook is simpler to operate.
- Time-only revalidation: rejected, editors need publishing to show up quickly.
- Webhook verification through `next-sanity/webhook`: rejected, see decision 3.
- Stega and click-to-edit overlays now: deferred, it requires stripping stega from every string that mappers, slugs and metadata use.

## Reasons

Tag ISR keeps pages static and fast, uses stable APIs, needs no team-wide change, and still gives on-demand freshness; the fetch seam keeps the later move to Cache Components cheap. Fail-closed webhook and Draft Mode endpoints mean a missing secret never opens anything. Deriving gates, redirects and sitemap eligibility from the route manifest and the `@vitalos/cms` gate functions keeps one source of truth.

## Trade-offs

Pages are only as fresh as the webhook (with a one-hour fallback). `revalidateTag(..., { expire: 0 })` makes the first request after a publish wait for the refresh. The root layout reads Draft Mode, which keeps visitor pages static today but would need a Suspense boundary under Cache Components. Mappers and templates written by other workstreams must pass tags through the fetcher for fine-grained invalidation; without tags they still refresh through the root tag. A private Sanity dataset would also need the token on published reads.

## Consequences

- The fetcher type (`SanityFetcher` in `src/lib/cms/fetch.ts`) is the contract workstream C2's `createSanityContentSource` is built against.
- `getContentSource()` is the only way pages obtain content; they never create Sanity clients.
- Sitemap correctness relies on `getSitemapEntries()` returning only published, non-`noindex` documents.
- Redirect additions are code-reviewed: they go through `generated.ts` or `redirect-map.ts` and the validator.
- Environment-specific behaviour (robots, `noindex`, Draft Mode availability) follows `@vitalos/config` (`features.indexable`, read token presence), never `NODE_ENV`.

## Revisit triggers

Content volume or edit frequency makes ISR refresh cost visible; the owner wants live preview with click-to-edit (stega) or live content; Next.js stabilises Cache Components for forms and `searchParams` in a way that removes the Suspense burden; the Sanity dataset becomes private; a CDN other than Vercel's fronts the site; redirects need patterns (for example whole retired sections).
