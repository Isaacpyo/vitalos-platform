# ADR 055 Admin AI & Data workspace: AI-assisted delivery, shared tokens, the first journey

- **Status:** Accepted (engineering), 28 Oct 2026. The live model provider stays off; nothing here enables it.
- **Builds on:** ADR-026 (Super Admin), ADR-040 (v1 request signing), ADR-042 (content tick), ADR-046, ADR-052 (AI & Data foundation), ADR-053.

## Context

`/ai-data/` was a pipeline, offers and a budget. Vitalos wins customer-funded engineering work and wants to turn proven, repeatable solutions into products, so the admin needs to carry one piece of work from enquiry to delivery with AI preparing and a person deciding. The live provider has no key in production, so every AI feature needs an honest "unavailable" state and a useful non-AI path.

## Decisions

1. **One workspace, one record type for generated work.** `Draft` (`apps.aidata`) holds a brief, discovery questions, a discovery pack or a proposal, with its source text kept unchanged beside what was derived, quoted evidence spans, warnings, the method (`ai`, `rules` or `manual`), versions and who reviewed and approved. It links to the opportunity and to the original enquiry, which is never modified. Opportunity, discovery and proposal live in `apps.aidata`; Project, Milestone and Deliverable belong to the client portal (ADR-056) and are not modelled here. `templates/aidata/_opportunity_extensions.html` is the empty slot the portal panel fills.
2. **The model proposes, a person decides.** Nothing is approved, sent, emailed or published automatically. A brief becomes an opportunity only when a person approves the preview. A discovery pack or proposal needs two human steps (review, then approve). An approved draft is never edited: a revision is a new version and supersedes the old one on approval. A proposal is drafted only from an approved discovery pack and the offer definition (`catalog.py`, from `docs/ai-data/commercial/03-offers.md`); it is assembled by rules, so no model can change scope or price. Prices are the existing `OfferPrice` or an estimate a person types, always labelled. Export is Markdown or a print view for the owner to send; each export is audited. Moving an opportunity to Proposal now requires an approved discovery pack (`services.change_stage`, enforced on the server).
3. **Unsupported claims are dropped.** Every model value that states a fact must come with a quote that is really in the supplied text (whitespace and case tolerant); otherwise it is discarded and a warning says so. Contact details and organisation are matched by rules first and are never replaced by a model. Workflow steps and requirements without a real quote are dropped; assumptions may have none and are labelled as assumptions. Blank fields stay blank and are listed as missing. No confidence percentages are invented: uncertainty is shown only as blank fields and fields the model flagged unclear.
4. **Untrusted input.** Pasted text and attachments (plain-text files, 100 KB, read in the browser) go only into the gateway's delimited data block (`neutralise`), never into instructions. Output is schema-validated (`additionalProperties: false`), so a model that "obeys" an injected instruction to add a price or an approval fails validation. Model output is inert text.
5. **Durable execution on the existing mechanisms, no new queue.** The `Draft` row is the task: `queued`, `running`, `failed`, `cancelled` plus the review states. A request creates the row (idempotent on a key) and runs it inline. Synchronous execution is acceptable because the gateway already bounds a run (per-call timeout, at most two retries, 40 s deadline) and because the row, not the request, owns the outcome. A run takes a 90 s lease renewed before the model call; if the process dies the content tick (ADR-042) and the status poll call `recover_stale`, which requeues while attempts remain (maximum 3) and otherwise marks the task failed ("interrupted"); the same tick runs queued tasks. Every transition is a conditional UPDATE, so two workers, a double submit, or a cancel racing a completion cannot run, finish or duplicate a task. Retries reuse the same row. The UI polls `/ai-data/drafts/<id>/status/` every 2 s while a task is active and reloads once it ends; status always comes from the database. A failure is visible, keeps the original text, and offers Retry, "Prepare without AI" and manual entry. If the model is unavailable (switch, key, cap) the non-AI path runs immediately and is labelled; an AI run that fails is `failed`, not silently replaced.
6. **Assistant, not chatbot.** A drawer scoped to one opportunity: fixed actions computed by rules (summary, what is missing, suggested next step) and a free-text question answered by the model only from numbered records of that opportunity, accepted only if it cites record ids that exist; otherwise "not answered". With AI off it is a labelled keyword search of the records. Questions are never stored; the audit keeps their length.
7. **Website brief assist.** `POST /api/ai-data/brief-assist/`, signed with the existing v1 scheme (ADR-040) under a new `assist` scope that uses the same keys as `read` and `tick` (no new secret). Order: keys configured (503), signature (401), feature switch "Website brief assist" (default OFF) and AI availability (503), validation (400), rate limits (429: 10 per visitor reference per 15 minutes, 40 per minute overall, counted from `BriefAssistEvent`), model call. It stores metadata and SHA-256 hashes only (`BriefAssistEvent`, `ModelExecution`), never the visitor's words. CSRF-exempt only because it is signed. Prompts `brief_questions@1` and `brief_draft@1`.
8. **Shared tokens.** `packages/design-tokens/src/ai-data-admin.ts` maps the marketing roles (`ai-data.ts`) and spacing, radii, shadow and motion (`primitives.ts`) onto the admin's light/dark/system theme, with denser spacing. A test writes `superadmin/assets/ai-data-tokens.css` (`UPDATE_TOKENS=1 corepack pnpm --filter @vitalos/design-tokens test`) and fails if it drifts or a pair misses its contrast minimum. Tailwind imports it, so `bg-aid-surface`, `text-aid-muted`, `border-aid-border` and the status colours are available.
9. **Components, not a framework.** Django `{% include %}` components (`templates/aidata/components/`), HTMX, native `<dialog>` for dialogs and the assistant drawer, the Popover API for "Why" reasons (shown inline where unsupported), a toast region fed by Django messages and `HX-Trigger`, CSS skeletons shown only while a request or task is active, a keyboard-resizable split panel (arrow keys, Home, End), and `static/js/aidata.js` (no dependency). Icons mirror the website's monoline set (24 grid, 1.5 stroke, square caps) in `aid_icon`. Motion is at most 200 ms and off under `prefers-reduced-motion`.
10. **Roles.** The existing gate is kept: SuperAdmin and ServiceLead act; Viewers and users without a role get 403 on every AI & Data page, because opportunities hold personal data (as enquiries). Services re-check the role. A read-only view for Viewers would need a redacted view of personal data and is a later decision.
11. **Funnel event.** Entering Qualified records an audited `aidata.opportunity_qualified` event (source, scorecard band, whether a brief exists, days since creation), with no prompts or text. Audit summaries and metadata never hold pasted text, contact details or model output.
12. **Evidence.** `manage.py aidata_eval` runs 22 reliability cases offline (incomplete, contradictory, unsupported, injection, provider failure, timeout, invalid JSON) with hand-written simulated responses and gates CI. It is reliability evidence only and says so; there are no live recordings and no live model-quality evidence.
13. **Retention.** Anonymising an opportunity also clears its drafts' source text and derived values. `aidata_retention` also deletes enquiry previews never turned into an opportunity after 30 days and brief-assist events after 90 days (dry run unless `--apply`; not scheduled by this change).

14. **Brief-assist hardening (security review).** Each call writes a `pending` event row before the model is asked and updates it to its outcome afterwards; the rate limiter counts pending rows (including the caller's own), so a burst of simultaneous requests is counted before any of them reaches the model, and a row abandoned by a crash keeps counting until its window ends. Brief assist is also held to a share of the daily run cap (`AI_DATA_BRIEF_ASSIST_DAILY_SHARE_PERCENT`, default 30%). Question ids returned to the website are always renumbered `q1`..`q4` in order (questions are de-duplicated by text), and the answer-id pattern accepted on the request matches the website's (`[A-Za-z0-9_-]{1,20}`; ids are only echoed as labels in the data block).

## Boundaries and later phases

- Delivery (tasks, test cases, progress, blockers), managed operations (incidents, exceptions) and product incubation (recurring-need evidence, reusable components) have navigation and honest empty states (`/ai-data/lifecycle/<stage>/`) and a description of the data each needs. No data is invented. Project, milestone and deliverable data arrive from the client portal when the main session connects it.
- AI drafting of proposal wording is deliberately not built: commercial text stays rules-assembled from approved inputs.
- The website client (W6) must sign requests with scope `assist` (`apps/web/src/features/content/signing.ts` scopes).
- Owner steps before live use: set `AI_DATA_LLM_API_KEY` in the secret store, switch on "Live model path" and "Website brief assist" in AI settings, run a live evaluation, and decide on scheduling `aidata_retention`.
