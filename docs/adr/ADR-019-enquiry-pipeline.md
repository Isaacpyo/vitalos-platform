# ADR 019 Enquiry pipeline

Status: Accepted for the local foundation. The enquiry retention policy was approved by the owner on 11 October 2026 (24 months after the last contact, then deleted) and is enforced by migration `20261011110000_enquiry_retention.sql` and a daily purge job (see Retention below). The production Supabase project, the email provider, Turnstile production keys and acknowledgement emails remain unapproved (stage-1 plan section 6).

## Context

Stage 8 section 20, Stage 9 section 15 and Stage 10 section 21 define the enquiry flow: server-rendered form, server validation, Turnstile when enabled, a durable record, an email notification and an optional acknowledgement. Email is a notification channel, not the database (Stage 0 section 11): an enquiry must survive a provider outage. The baseline only validated input and then answered 503: no persistence, rate limiting, human verification or notifier. ADR 006 chose Supabase PostgreSQL with a durable outbox; this ADR records how the pipeline is built on it.

## Decision

1. **Layers.** `apps/web/src/features/enquiries` is split into `domain` (model, events, ports), `application` (`receiveEnquiry`, `dispatchOutbox`), `adapters` (Supabase, Postgres rate limiter, Turnstile, memory, console) and `composition.ts`. Domain and application import no framework or provider; they depend on ports (`EnquiryRepository`, `RateLimiter`, `HumanVerifier`, `OutboxStore`, `Notifier`, `Clock`, `EnquiryLogger`). Route handlers and the server action are thin adapters over the same service.

2. **One contract.** `@vitalos/validation` exports `enquirySchemaV2` (`.strict()`), shared by the JSON route and the server action. Fields: name, organisation, workEmail, role?, goal (20 to 5000), timeframe, budgetRange?, intent, offerSlug?, sourcePath, utm (bounded), consent (literal true), privacyNoticeVersion, idempotencyKey (uuid), turnstileToken?, honeypot `website` (must be empty). Error messages explain the fix and never echo the submitted value.

3. **Result model.** `receiveEnquiry` returns `accepted | invalid | rejected | rate-limited | unavailable`. Order: validate (cheap, local), abuse signals (honeypot, unknown keys: `rejected`, never a field error), privacy notice version check, per-IP rate limit, idempotency lookup, Turnstile, global rate limit, persist. A replayed idempotency key is answered with the original reference before Turnstile runs, so a retry after a lost response neither fails on a spent token nor spends budget. The global bucket is charged only after the human check has passed, so a flood of failing tokens cannot exhaust it and lock real visitors out. Any dependency failure is `unavailable` (fail closed, HTTP 503); the log line carries the SQLSTATE or adapter code, never the message. Input that PostgreSQL cannot store is a validation error (400): the schema rejects NUL, ill-formed Unicode and CR/LF in one-line fields, and measures lengths in code points like `char_length`; UTM is bounded by UTF-8 bytes. With no backend configured the service is honestly unavailable.

4. **Atomic write and idempotency.** `public.submit_enquiry(p jsonb)` inserts the enquiry and its outbox row in one function body (one transaction) and returns `{id, reference, duplicate}`. `idempotency_key` is unique; a replayed key returns the original reference and writes nothing. Only the `internal-notification` outbox row is enqueued. The `acknowledgement` kind is reserved in the schema and dispatcher but is not enqueued until the owner approves customer acknowledgements.

5. **Outbox and dispatch.** The outbox row is the durability guarantee. `claim_outbox_batch` uses `FOR UPDATE SKIP LOCKED`, increments `attempts` and takes a five minute lease, so concurrent dispatchers never share a row; expired leases, including rows with a null lease, are reclaimed. `attempts` is the lease token: `mark_outbox(id, attempts, state, ...)` only updates a row still `processing` with that exact value, so a stale worker cannot overwrite the outcome of the worker that re-claimed the row. `dispatchOutbox` retries with bounded exponential backoff (60 s doubling, capped at 1 h), dead-letters after five attempts or on a non-retryable error (`state = failed`, visible to operators) and stores only an error code, never a provider message. Delivery is at-least-once; each message carries `enquiryId:kind` as its idempotency key. Events follow the Stage 0 section 42 envelope (`enquiry.received.v1`) and carry identifiers only, never personal data.

6. **Dispatch trigger.** After an accepted enquiry the route handler or action calls `after()` for best-effort dispatch. That is an optimisation only: if it never runs, the row stays pending. `/api/internal/outbox/dispatch` (Bearer `OUTBOX_DISPATCH_SECRET`, compared with timing-safe digests, 503 when the secret is unset) drains a batch. `apps/web/vercel.json` schedules one daily Vercel Cron call (Hobby plan limit) as the safety net; Vercel sends `Authorization: Bearer $CRON_SECRET`, so the route accepts `CRON_SECRET` or `OUTBOX_DISPATCH_SECRET`. `after()` stays the immediate path. `tooling/scripts/dispatch-outbox-local.mjs` is the manual trigger.

7. **Abuse controls.** Same-origin check (Origin must match the site origin or the request host; `Sec-Fetch-Site`, when present, must be `same-origin`), JSON content type required, body capped at 32 KiB while streaming (Server Action bodies are capped at 64 KB through `serverActions.bodySizeLimit`), unknown keys and a filled honeypot rejected, rate limits per hashed IP (10 per 10 minutes) and globally (300 per hour) in `rate_limit_buckets` through `rate_limit_consume`, Turnstile verified server-side (action `enquiry` pinned, hostname pinned in production). A Turnstile provider outage is `unavailable`, not a pass. Cloudflare's documented dummy secrets (`1x`, `2x`, `3x`) are answered locally without calling Siteverify (they are rejected in production), so tests and local work never depend on the network: a Siteverify timeout on a busy runner was the cause of an intermittent "Enquiries are unavailable" in the end-to-end suite. Production never runs without Turnstile: `@vitalos/config` requires both keys, `ENQUIRY_IP_HASH_SALT` and `ENQUIRY_PRIVACY_NOTICE_VERSION` when `VITALOS_ENQUIRY_BACKEND=supabase`, rejects Cloudflare's documented dummy keys, and the composition root refuses to build a service without them (the disabled verifier is unreachable in production). The client address is taken from `x-vercel-forwarded-for`, then `x-real-ip`, then the first valid hop of `x-forwarded-for`, skipping malformed values. Server Actions are additionally protected by the Next.js Origin/Host comparison, which this code relies on but does not replace (a request with no `Origin` header is allowed through by the framework with a warning, which is why validation, rate limiting and Turnstile run regardless).

8. **Privacy.** Logs go through `@vitalos/observability` (shared redaction) and never contain name, email, goal or organisation. The IP address is stored and used for rate limiting only as an HMAC-SHA-256 under `ENQUIRY_IP_HASH_SALT`; the Supabase backend refuses to run without the salt. Database error messages (which embed the failing row) are never logged: the adapter keeps only the SQLSTATE. `retention_until` is set by a database trigger to `received_at` plus 24 months (owner decision, 11 October 2026) and enforced by the purge job (see Retention). Consent time and the privacy notice version are stored with each enquiry; the version is accepted only when it equals the server's `ENQUIRY_PRIVACY_NOTICE_VERSION`, so consent is never recorded against a client-chosen label (a mismatch asks the visitor to reload and confirm again; the contact page reads the same value on the server). `sourcePath` is a bare site path (no query or fragment). References carry 48 bits (`VIT-` plus 12 hex characters).

9. **Database access.** The four functions are `SECURITY DEFINER` with `set search_path = ''`, revoked from `public`, `anon` and `authenticated` and granted to `service_role` only; the tables stay revoked from `anon` and `authenticated` with RLS enabled. The web app uses the server-side secret key behind `server-only`, with sessions disabled. pgTAP (`supabase/tests/002_enquiry_v2.sql`) asserts privileges, atomicity, idempotency, constraints, claim/lease/retry and the limiter.

10. **Flags and accepted risks.** `budgetRange` is off: `approvedBudgetBands` is empty until the owner approves bands, so the field is rejected if sent. The timeframe identifiers (`immediately`, `within-3-months`, `within-6-months`, `exploring`) are provisional and need owner approval. Accepted risks: (a) the Turnstile hostname is pinned in production only; preview and staging use generated hostnames, so there only the action is pinned; (b) the rate limit assumes Vercel overwrites the forwarding headers, and elsewhere a spoofed address could evade the per-IP limit (the global limit, Turnstile and idempotency remain); (c) the NOT VALID check `enquiries_v2_required` is also evaluated when an existing row is updated, which is harmless because no pre-v2 rows exist (the production project is unapproved and the table has only been written through `submit_enquiry`); if such rows ever exist the constraint must be made conditional on a v2 marker before they are updated.

## Options

- Email only, or a provider webhook as the record: rejected, an outage would lose enquiries.
- Direct table inserts with row-level security from the browser: rejected, it exposes the schema and removes server-side validation and abuse controls.
- A queue service or workers now: rejected for Stage 1 (Stage 0 section 43: do not add infrastructure before it is needed). The Postgres outbox keeps the contract so a worker can take over later.
- In-memory or edge rate limiting: rejected for production, state would not be shared across instances; kept only as the memory backend for tests.
- Fire-and-forget `after()` as the only delivery path: rejected, it is not durable.

## Reasons

A single contract and one service behind ports keep the route handler and the server action identical and let tests exercise every result without a database. Atomic function writes and the outbox give durability and recoverability. Hashing the IP and logging only identifiers meets the data-minimisation requirement of Stage 10 section 25.

## Trade-offs

Fixed-window rate limiting allows a burst at a window boundary. The outbox is polled, so notification latency depends on the trigger until a scheduler is approved. The function-based interface couples the web app to function signatures; they are versioned by migration. Turnstile needs JavaScript, so the no-JS native POST cannot pass verification when Turnstile is enabled.

## Consequences

Contact page work (H) binds `submitEnquiryAction` and the `EnquiryFormState` type. A real email adapter implements `Notifier` once a provider is approved. A runbook for delivery failure (workstream I) should cover dead-lettered rows (`state = 'failed'`). Retention is implemented (see Retention below).

## Revisit triggers

Owner approval of timeframe or budget bands, retention policy, acknowledgement emails, an email provider, Turnstile production keys or a scheduler; sustained enquiry volume that outgrows the polled outbox; an approved existing datastore (ADR 006).

## Status note (2026-10-10)

The decision above is unchanged. The "real email adapter" named in Consequences now exists behind the `Notifier` port, selected by `EMAIL_PROVIDER` (`none`, `console`, `postmark`, `resend`). The email provider itself is still **not approved**: the choice between Postmark and Resend, the sender domain and the API key remain owner inputs, and no real values are configured anywhere. Both adapters were tested only against a fake `fetch`; no real provider API has been called.

- Adapters: `apps/web/src/features/enquiries/adapters/email-notifier.ts`, wired in `composition.ts` from `EMAIL_FROM`, `EMAIL_PROVIDER_API_KEY` (server-only) and `ENQUIRY_NOTIFICATION_TO`. Requests use the injected `fetch` with a 10 s `AbortSignal.timeout` and carry only sender, recipient, subject and a plain-text body (plus the enquirer's address as reply-to only when it is a plain safe address).
- Failure semantics for the outbox: network errors, timeouts, 408, 409 (Resend, identical request in flight), 429 and 5xx are retryable; 401/403 (authentication), 400/422 (validation) a 3xx redirect (not followed, `email-redirect`) and any other status are permanent and dead-letter the row. Only a short error code is stored (`email-network`, `email-timeout`, `email-rate-limited`, `email-provider-unavailable`, `email-auth-rejected`, `email-rejected`, `email-redirect`, `email-http-<status>`); provider response bodies are never read, stored or logged.
- Privacy: the subject carries the reference and intent only, never the goal. The body carries the enquiry for the internal recipient. Logs carry provider, kind, reference, correlation id and HTTP status only. The reserved `acknowledgement` kind is refused (permanent `email-kind-unsupported`): no email is sent to a prospect until the owner approves acknowledgements.
- Configuration rules (`@vitalos/config`): `postmark` or `resend` requires `EMAIL_FROM`, `EMAIL_PROVIDER_API_KEY` and `ENQUIRY_NOTIFICATION_TO`; in production `EMAIL_PROVIDER=none` is rejected once `ENQUIRY_NOTIFICATION_TO` is set (a recipient with no provider would silently never notify), and `console` stays rejected. With neither set, production still starts with `none` and the manual runbook procedure applies.
- Delivery stays at-least-once. Resend receives the `<enquiryId>:<kind>` idempotency key as an `Idempotency-Key` header; Postmark has no equivalent, so a re-delivery after a crash between send and `markSent` can produce a duplicate internal email, which is acceptable for an internal notification.
- Still open: the scheduler that calls the dispatch endpoint, provider approval, sender domain verification (SPF/DKIM/DMARC), and a data-processing agreement with the chosen provider.

## Retention (2026-10-11)

The owner approved the policy: enquiries are kept 24 months after the last contact, then deleted. The privacy notice says exactly that, so the system enforces it.

- Migration `supabase/migrations/20261011110000_enquiry_retention.sql`: a BEFORE INSERT trigger sets `retention_until` to `received_at` plus 24 months when the insert does not supply one (so `submit_enquiry` is unchanged), existing null rows are backfilled the same way, and `purge_expired_enquiries()` deletes enquiries with `retention_until < now()` together with their `notification_outbox` rows (the foreign key is `ON DELETE RESTRICT`, so outbox rows are deleted first) and returns the number of enquiries deleted. It is SECURITY DEFINER with an empty `search_path`, executable by `service_role` only.
- There is no last-contact field, so the clock starts at `received_at`. Extending retention for a conversation that is still active is a deliberate manual update of `retention_until`; nothing extends it automatically. If follow-up contact is later recorded in the database, the trigger and the purge can key off that instead.
- Trigger: `apps/web/vercel.json` runs a second daily cron (`30 3 * * *`, UTC) against `/api/internal/retention/purge`. It is a separate route rather than a step chained onto the dispatch route: dispatch returns 503 whenever no notifier is configured (today's production state), which would otherwise block the purge, and the two jobs fail and are monitored independently. It authenticates exactly like dispatch: `Authorization: Bearer` with `CRON_SECRET` or `OUTBOX_DISPATCH_SECRET`, timing-safe comparison, 503 when neither is set. No new environment variable. GET and POST are accepted.
- Responses and logs carry a count only (`{ "status": "ok", "purged": n }`, log event `retention.purged`); a store failure answers 503 `unavailable` with no detail.
- Out of scope: copies the application does not control (Supabase backups, the email provider's sent-mail records, the internal recipient's mailbox) age out under their own policies; the privacy notice and processor records should say so.
- The migration must be applied to the production Supabase project through the release process before the purge route runs there; until then the route answers 503 (the function does not exist) and nothing is deleted.

## Status note (2026-10-12): notification email redesign

The owner asked for an internal notification that can be triaged from the inbox, on a phone, in dark mode. This supersedes the 2026-10-10 privacy line on the subject; everything else above is unchanged.

- Template: `apps/web/src/features/enquiries/adapters/enquiry-notification-email.ts` renders the subject, a plain-text part and an HTML part. The adapters now send both parts (`TextBody`+`HtmlBody` for Postmark, `text`+`html` for Resend), which the providers deliver as multipart/alternative. Sender, recipient, Reply-To, idempotency, retries and error mapping are unchanged.
- Subject: `New enquiry: {intent label} · {name}, {organisation} · {reference}` (organisation left out when empty). **Privacy change:** the subject now carries the enquirer's name and organisation, and the hidden HTML preheader carries the timeframe and the first 80 characters of the goal. Both can show in inbox lists and phone lock-screen notifications for the internal recipient (`ENQUIRY_NOTIFICATION_TO`). The goal is never in the subject. Logs are unchanged and still carry identifiers only.
- Every value is cleaned (control and bidi-override characters removed) and HTML-escaped; single-line fields are folded onto one line and plain-text goal lines are quoted with `> `. The HTML has no scripts, remote images, remote fonts or tracking. The header logo (the Vitalos logo recoloured white) and the footer social icons (Font Awesome Free brand glyphs, CC BY 4.0) are inline CID attachments (`email-inline-images.ts`, from `adapters/assets`), so nothing is fetched. The footer also carries the legal name, company number and registered office from `@vitalos/cms/repo` settings, and the owner-supplied LinkedIn, X, Instagram and Facebook profiles (`/vitalos`). Links are a `mailto:` reply to the enquirer (subject `Re: Your Vitalos enquiry ({reference})`), the public source page and the social profiles. Colours come from `@vitalos/design-tokens`; light and dark text pairs are tested for WCAG AA.
- There is no per-enquiry admin link: web enquiries are stored in Supabase and are not forwarded to the Super Admin (see `superadmin/docs/email-setup.md` section 12), so the email has no "View in database" button.
- Local preview: set `EMAIL_PREVIEW_DIR` and run `enquiry-notification-email.preview.test.ts`; it writes HTML, plain-text and `.eml` files for the sample and edge-case variants. Real-client rendering (Gmail Android/iOS/web, Apple Mail, Outlook) still needs an owner-approved test send to `support@vitalos.co.uk`.
