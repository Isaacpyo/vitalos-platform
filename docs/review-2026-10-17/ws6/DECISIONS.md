# WS6 decisions (Relay quality and cost)

| # | Finding | Decision | Reason |
|---|---|---|---|
| 1 | E1 | `handoffRate` is a **fraction (0–1)** in the admin API and the `digest.daily` webhook. relay-core computes it with `handoffRate()`, capped at 1. Django keeps formatting `fraction × 100`. | The Super Admin, its fake and its fixtures already treated it as a fraction, so one fix on the website side and a documented unit (docs/relay/API.md) keep both sides consistent. |
| 2 | D1 | The 509,640-token figure is **period usage divided by real conversations**, not the prompt size. `relay.usage_daily` counts every model call: answers, hand-off summaries, stopped streams and the eval and load harnesses, which delete their conversations afterwards. Fix: tag usage by source (`relay.usage_by_source`), mark harness traffic with `utm_source=relay-eval\|relay-load`, and show per-answer input tokens (average, p95, maximum from `messages.tokens_in`). The daily cap still uses `usage_daily`. | Changing retrieval alone would neither explain nor fix the number. A visitor could set the same utm_source, but that only moves their own usage into the "test" column, and it still counts towards the cap. |
| 3 | D1 | Keep the budget-leak fixes anyway: each chunk capped at 450 tokens, sources at 2,400, history at 2,000 tokens, 8 turns and 600 per turn, and a hard total of 8,000 per call. A chunk that is too large is skipped, not kept. FAQ chunks split at 300 words. Conservative estimate: `max(words × 1.33, chars / 4)`. | No stored content can make one turn expensive, and the eval proves the ceiling. |
| 4 | D2 | Typo tolerance comes from a vocabulary-based corrector in relay-core (edit distance, same first letter, at least 5 letters), used by both stores. Postgres supplies the vocabulary through `relay.kb_vocabulary()`. No `pg_trgm`. | One mechanism for the memory and SQL paths, no extension, deterministic tests. |
| 5 | D2 | Small talk (greeting, thanks, goodbye, acknowledgement) gets a fixed reply: no retrieval, no model call, no gap. The replies reuse the Settings greeting wording. | Zero cost. "Hello" used to be recorded as a gap. |
| 6 | D2 | The four new knowledge entries are `status: draft` + `confirmation: needed` in `packages/relay-knowledge/content/`. To approve one, set `status: published`, delete the `confirmation` line and run `build-content`. The eval runs both ways. | Repo entries publish on ingest, and the brief asks for "Needs confirmation". Drafts are ingested (visible in the admin) but never retrieved. |
| 7 | D2 | The founder entry uses only the published author profile text, fetched by GET from vitalos.co.uk/insights/introducing-vitalos and /insights/authors/temitope-agbola on 17 Oct. | Integrity rule 0.4. |
| 8 | D2 | "Suggested answer" drafts a `team_answer` from the best-matching published chunk and opens the editor. It never publishes and never demotes an answer that is already published. | Draft only, per the brief. |
| 9 | D3 | Django sends `display_name` (once WS7 adds it) or `full_name`, else "Vitalos team"; never the email. The website shows visitors only the first word (`publicStaffName`), in normal case: "Temitope · Vitalos". | Two layers: if an old Django deploy still sends a username, the website catches it too (anything with `.`, `_`, `@` or digits falls back to "Vitalos team"). |
| 10 | D4 | Hourly ingest via pg_cron → `/api/relay/cron/ingest` at :12 (Vault-gated, like the other Relay jobs). The last-sync age comes from `kb_sync_runs` (the CLI and the cron both record runs), with a warning after 24 h. Overview counts are served at `GET /api/relay/admin/overview`, with `client.overview()` and the fake. | ADR-038: no Vercel cron (daily only on this plan), no GitHub schedule (public repo rule). No cost. |
| 11 | D5 | "Leave your email and we'll reply" reuses the existing hand-off form (name, email, consent). That form already stores the details on the conversation and alerts the team, so no new column. `RELAY_VISITOR_EMAILS_ENABLED` is unchanged. | One way of collecting contact details, with consent text that is already approved. |
| 12 | D6 | Thumbs-down shows three one-tap reasons plus Skip, and the hand-off card follows the choice. A second feedback call with a reason stores only the reason. | No double-counted gap. Keyboard focus moves to the first reason. |
| 13 | C2 | The panel is mounted only while open: it unmounts on close, so `inert` is not needed. It restores without asking only for `?relay=resume` or a conversation chosen or started in the same tab session (sessionStorage `vitalos.relay.chosen`). While closed, the unread badge polls a count every 20 s for conversations a person has joined. Answers are `div role="group"` with an `aria-label`. | The closed DOM holds no transcript, and email resume links keep working. |
| 14 | Analytics | The widget emits a `window` CustomEvent `vitalos:relay` with `{type}` (`relay_opened`, `relay_question`, `relay_handoff`) and exports `RELAY_EVENT`. WS5 or the orchestrator wires it to `track()`. | The widget may not import apps/web. |
| 15 | Decision 1 | "Five practices/solutions" becomes six in the system prompt and repo knowledge. The Master FAQ snapshot is not edited because it is synced from Notion. Entries ABT-01, LAB-01, WWD-01 and WWD-12 still describe five practices with Labs as separate; they are listed for the owner. | The snapshot is generated from Notion. |
| 16 | Infra | The worktree moved to `D:/Development/vitalos-ws6` (C: was full), per the orchestrator's instruction. | Disk space. |

No new dependencies.
