# WS3 decisions (Insights content operations)

Decisions taken during the 17 Oct 2026 run, with reasons. Numbered for reference from NOTES.md and the report.

1. **Draft is the import command's default.** `import_insights_batch --apply` now creates or updates drafts (`--status draft`); publishing needs the explicit `--status published`. *Reason:* the run (RUN-PROMPT 0.1, 0.2) allows drafts only, and a default that publishes is one missed flag away from publishing 20 posts in production. The first version's behaviour is still one flag away for the owner once publishing is approved.
2. **A draft import approves nothing.** Without `--status published` the import does not record the founder approval on the "Vitalos" organisation author (it is created and activated only), and ticks no editorial check. *Reason:* the approval and the checks are editorial statements the owner makes before publishing; a draft import should not make them on his behalf.
3. **Author: the files name "Vitalos"; the run asks for Temitope Agbola.** Every batch-2 file has `authors: [Vitalos]`, and 00-INDEX says the organisation author was the plan (owner-approved on 16 Oct per `importing.py`). The run brief (17 Oct, later) asks for "author Temitope Agbola". The command gains `--author SLUG|EMAIL`, which puts every post under an **existing, active person author** (found by slug, or by the email of the author's linked dashboard user). It never creates or confirms a person author, because only the real person can approve their own profile. Without `--author` the files' organisation author is used. *Reason:* the repo has no person Author record for Temitope (no seed or migration creates one; production state cannot be read from this run). The published "Introducing Vitalos" post has an author profile in production, so a person author very likely exists there; the production command in NOTES.md therefore runs a dry run first that names the resolved author, and falls back to the files' author if the person author is not found. Owner to confirm the slug (approval item).
4. **The editor's author list offers confirmed, active authors only**, plus the post's own authors whatever their state (labelled "not confirmed" / "inactive"), so an edit never drops an author silently. *Reason:* the brief asks for a multi-select of confirmed authors, and only confirmed authors can be published; a new author is confirmed in Insights > Authors first (the help text says so).
5. **Author order is the order of the ticked boxes on screen.** The control is a checkbox list (works without JavaScript: the post's authors are listed first in byline order, a newly ticked author is added after them). With JavaScript, ticking moves an author to the end of the byline, unticking moves them out, and Up/Down buttons reorder; a "Lead" badge marks the first. The browser submits checkboxes in document order, so no hidden order field is needed. `MAX_AUTHORS` (4) is enforced on the server ("Choose at most 4 authors.") and, with JavaScript, by disabling further boxes at the limit. *Reason:* a native `<select multiple>` cannot express order and is hard to use with a mouse; this is one control with no second ordering mechanism.
6. **Cover upload: a new shared partial, `templates/insights/_file_drop.html`.** The admin had no styled file control (enquiry and careers attachments use the native input), so this is the first one, not a second pattern. It keeps the native `<input type=file>` visible and styled with Tailwind's `file:` variant, so it works without JavaScript; the editor script adds drag and drop, client-side type and 5 MB checks and an inline preview. The preview uses a `data:` URL because the admin CSP allows `data:` images and not `blob:`. Follow-up: move the behaviour from `insights-editor.js` to `app.js` when another screen (author photo, careers) adopts the partial.
7. **Word count and reading time use the website's rule**, which is `apps/content_sync/formatting.py` `reading_minutes` (the admin computes `readingMinutes` for the content API, and the website shows it as is): words match `[0-9A-Za-zÀ-ɏ]+(?:['’-][0-9A-Za-zÀ-ɏ]+)*`, minutes are `max(1, ceil(words / 220))`. The script copies the pattern and a test asserts it is identical to the Python one.
8. **Layout: secondary panels move under the editor.** Call to action, Search, Updates and related posts, and Revisions now sit in a two-column grid under the editor; the rail keeps status and publishing, checks, address, authors, topics, cover and homepage, and spans both rows (`xl:grid-rows-[auto_1fr]` so the rail's height never opens a gap under the editor). *Reason:* removes the empty left column and shortens the rail by four cards without nested scroll areas.
9. **Article closing action pre-selects the contact intent.** When the post's call to action is the plain `/contact` (the admin default and every batch-2 file) or empty, the closing card links to `/contact?intent=…` from the post's practice: Engineering → `engineering`, AI & Data → `ai`, Managed Services → `managed-services`, anything else → `project`. The label stays "Talk to Vitalos" (the site's locked CTA label) rather than a new "Talk to us". Any other link the editor set is kept.
10. **Index: filters and the feed link need more than one post.** With one published post the index shows that post as the featured card and no format tabs, topic links or feed link (they would only lead back to the same post). A format view always keeps its tabs (the way back to All). The visible "RSS feed" link sits beside the topic links; `<link rel="alternate">` autodiscovery stays as it was (WS5 owns site-wide autodiscovery).
11. **Already built, verified rather than rebuilt (PR #56 and earlier):** share menu with LinkedIn, X and Copy link (plain links, no scripts), related posts by shared topic (at most three, only when they exist, computed by the admin's `Catalogue.auto_related`), author block with photo or initials and the author page link, "Updated {date}" from the contract's `updatedAt` (set only for material updates), reading time. The finding B14 was observed on production before #56 deployed. The author photo comes from the admin's author avatar (content API `avatar`), so `MediaSlot` (repo-file media) is not used for it; a person without a photo keeps the initials, so production never shows an empty slot.
12. **Media library: from `MediaAsset` rows, not bucket listing.** See NOTES.md (shipped or follow-up).
