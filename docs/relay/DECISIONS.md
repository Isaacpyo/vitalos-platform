# Vitalos Relay: decisions

Each entry: what was missing or conflicting, what was chosen, and why. Owner decisions still open are marked **OWNER**.

1. **Specification text.** The v2 build prompt was cut off at 50,000 characters, in the middle of the system prompt. Sections after that point (fixed facts, summary, knowledge, realtime, security, configuration, phases, evals, report) come from v1 (`Claude outputs/Vitalos-Relay-Claude-Code-Prompt.md`, same sections renumbered). v2 wins where both cover a point.
2. **AGENTS.md over the prompt.** Supabase never runs on the laptop. Development uses VM slot 1 (`scripts/vm-slot.sh`). The work lives in the worktree `.claude/worktrees/relay` on `feat/relay` so the owner's uncommitted work in the main checkout is untouched.
3. **The repo serves the live site.** Vercel `vitalos-platform` serves www.vitalos.co.uk in production. The prompt said not to touch the live site without approval, so everything visitor-facing sits behind `RELAY_ENABLED` (default off; off in production). Merging is safe because the launcher does not render and every `/api/relay/*` route answers 404 until the flag is on. **OWNER:** turning it on in production.
4. **Super admin is Django with its own database.** ADR-026 and ADR-029 reject sharing the website database. The Relay tab is a Django app (`superadmin/apps/relay`). It reads and changes conversations through a **signed server-to-server admin API** on the website (`/api/relay/admin/*`, HMAC-SHA256, `RELAY_ADMIN_API_SECRET`). The website pushes alerts to Django through a **signed webhook** (`/api/inbound/relay`, `RELAY_WEBHOOK_SECRET`), the same pattern as enquiries. Conversation business rules live once, in `@vitalos/relay-core`. ADR-031.
5. **Admin auth reuses Django's** (password, axes, TOTP). The inbox needs SuperAdmin or ServiceLead, like Enquiries. Settings and knowledge publish/archive need SuperAdmin. No magic-link or second sign-in system was added. Entra SSO stays Phase 2 of the Super Admin.
6. **Admin alerts are delivered by Django.** In-app alerts, the Relay bell, toasts, email alerts, reminders' email, the digest, per-user preferences and the 10-minute dedupe use Django models (`RelayNotification`, `RelayAlertLog`, `RelayPreference`) and Django's existing Resend mailer and shared email layout (ADR-030). So `relay.notifications`, `relay.notification_log`, `relay.admin_prefs` (except presence) and `relay.email_outbox` (for admin mail) from the prompt are not created in the website database. One sending path per app (prompt rule: never add a second way). Visitor reply emails (off by default) are sent by the website, which owns the visitor's data and resume tokens. They are logged in `relay.email_outbox`.
7. **New Django models instead of new `Notification` kinds.** New kinds would need an `AlterField` migration, which stops the Super Admin's automatic deploy. Relay has its own bell in its top bar (as the boards show), backed by `RelayNotification`.
8. **Email alert design.** Admin alert emails use the shared layout (ADR-030, `layout.py`) with Relay content (eyebrow "RELAY · NEEDS A PERSON", headline, trigger, quoted message, details, button, paste link, footer lines from section 4.12). The layout's fonts, logo and colour tokens replace the board's bespoke ones, so every Vitalos email stays one family.
9. **Realtime.** "Ping, then fetch" over Supabase Realtime Broadcast on the website project, through a ~100-line Phoenix WebSocket client in the widget instead of `supabase-js` (keeps the panel bundle small). Pings carry no content. The server broadcasts through the Realtime HTTP API with the secret key. The publishable key and URL come from the conversation API, not build-time env. The Super Admin's Relay pages open the same socket (CSP `connect-src` widened on those pages only) and fall back to polling every 10 s. Elsewhere in the dashboard, toasts poll Django every 20 s (local rows only).
10. **Scheduler.** Vercel crons on this plan are daily only. The 5-minute reminder sweep, the hourly digest check and nightly retention use Supabase `pg_cron` + `pg_net`, calling the website's cron routes with `CRON_SECRET` held in Supabase Vault. Pre-authorised as Supabase project configuration.
11. **Tokens.** `@vitalos/design-tokens` is locked (ADR-008/016) and differs from brand v2. Relay adds a separate `relay` token scope (brand v2 values from `brand/tokens.json`, light and dark, CSS variables `--relay-*`) inside the token package, so the raw-colour gate holds and site tokens are unchanged. **OWNER:** move the site to brand v2 (the Super Admin already uses it), or point Relay at the site tokens.
12. **Fonts.** Manrope, Inter and JetBrains Mono through `next/font/google`. They are self-hosted at build, CSP-safe, `preload: false`, and scoped to the widget root, so pages without an open panel download no extra font files.
13. **Persistence across pages.** Full-document navigation means the launcher and panel are mounted on every page load and restore from `localStorage vitalos.relay.v1` (guarded). An open panel reopens on the next page.
14. **Knowledge sources.** Sanity is gone (ADR-028), so the "WEBSITE · CMS" source is the published repo content (`@vitalos/cms/repo`: practices, solutions, offers, industries, trust items, How we work). It is ingested with `source = 'cms'`. The CMS webhook is replaced by re-ingesting on pushes to `main` that touch content. `RELAY_CMS_SYNC_ENABLED` is not needed. "RELAY KNOWLEDGE · REPO" is `packages/relay-knowledge/content/*.md`. "TEAM ANSWERS" come from the admin.
15. **Data access.** supabase-js with the secret key, like enquiries, using the `relay` schema (`.schema('relay')`). The schema is added to the exposed API schemas. RLS is on with no anon or authenticated policies, and only `service_role` has privileges. The visitor never talks to PostgREST.
16. **Embeddings.** Edge Function `relay-embed` (gte-small, 384-d) as specified. When it is unavailable, retrieval is full-text only. Confidence then uses a calibrated full-text score (documented in `retrieval/confidence.ts`), and evals run on both paths.
17. **Admin identity in the website database.** `admin_id = "sa:<Django user id>"`, with the display name and initials stored on each admin message and join, so the website never needs the user table.
18. **Practices and call to action.** **Six practices**: Consulting, Engineering, AI & Data, Experience, Managed Services and Labs. The reference README chose the five from the 12 Oct design options, but the owner's Master FAQ follow-up (15 Oct) corrects this. The Master FAQ (entry ABT-01, checked against S1–S20 and Company HQ), Company HQ and the homepage design all say six. This applies to the fixed facts, seed knowledge and evals. Call to action "Talk to Vitalos" (website designs).
19. **Privacy notice version for hand-off consent.** The consent tick records `RELAY_PRIVACY_NOTICE_VERSION`. The published notice (`2026-10`) does not yet describe Relay or DeepSeek. Production stays off until the Relay section is approved. **OWNER:** approve `docs/relay/PRIVACY.md` and the notice version.
20. **Retention.** The job exists (`relay.purge_expired`) with Settings-driven periods (default 90 days without contact, 12 months with contact). It is not scheduled in production until the owner confirms the periods (prepared SQL in the report). **OWNER.**
21. **DeepSeek.** No API key exists on this machine. The real `DeepSeekProvider` is built and tested against a stubbed HTTP layer. Tests, previews and evals use `MockProvider` (`RELAY_LLM_PROVIDER=mock`). Model `deepseek-flash` with thinking disabled (verified on DeepSeek's pricing page, 15 Oct 2026). **OWNER:** sign in at platform.deepseek.com, create the key, top up credit.
22. **HubSpot** button rendered disabled ("phase 2"), as drawn.
23. **Master FAQ (Notion) follow-up.** Folded into this build. The snapshot and ingest are in Phase 1; sync, admin views and evals are in Phase 5. Source `faq`, Verified entries only, `[CONFIRM: …]` blocks stripped, and hold rules applied before anything is stored as publishable. `Source` and `Confirm note` never leave admin metadata. The 15-minute incremental and nightly full sync run on `pg_cron` (decision 10), not Vercel Cron. ABT-01 says "five practices … with Vitalos Labs as a separate research and technical proof capability", WWD-01 says Labs "sits alongside" the five, and WWD-12 says "Vitalos Labs is the sixth Vitalos practice". 25. **Launcher and header symbol.** The widget uses `apps/web/public/brand/vitalos-symbol.png`, the same 128 px resize of the supplied symbol (`brand/logos/vitalos-symbol.png`) that the Super Admin serves (6 KB instead of 220 KB). Like the footer logo it is an interim raster until the Figma vector exports exist (`docs/brand/asset-approval.md`); swap in the SVG when produced. The launcher label uses the site's font stack, so ordinary page views download no extra font. Manrope, Inter and JetBrains Mono (the same self-hosted OFL files as the Super Admin, through `next/font/local`) load only when the panel opens.
26. **Retrieval calibration (Phase 5, 15 Oct).** The first paraphrase eval scored 81.8% in the top 3, below the 85% target, and 25 of 88 real questions fell below the 0.55 answer threshold. Three changes, measured in `docs/relay/evals/REPORT.md`:
    - FAQ chunks are embedded on the question and short answer only. The full answer stays in the chunk for full-text search and for the model. gte-small reads 512 tokens, so long answers diluted the match with short visitor questions. `FAQ_EMBEDDING_VERSION` is part of the checksum, so the next ingest re-embeds every entry.
    - Retrieval over-fetches and returns each document's best chunk first (`diversify`), so one long page cannot fill the top slots and the three citations.
    - The default answer threshold is 0.40, down from 0.55. Off-topic questions top out at 0.27 and paraphrased real questions have p10 0.46. The threshold stays editable in Settings.
27. **Security review (Phase 6, 15 Oct).** The static review of every route found no flaw an anonymous visitor could exploit in authentication, signing, RLS or rendering. Fixed on this branch:
    - **M1.** A ServiceLead's edit to a published team answer now returns it to draft and removes it from retrieval. Only a SuperAdmin can publish.
    - **M2.** The admin realtime topic is derived from the admin secret, not the fixed `relay:admins` (ADR-034).
    - **M3.** Hand-off is rate-limited per conversation and sends one alert and one summary per open hand-off. Summary tokens and aborted streams (estimated) count against the daily cap. Feedback, end, resume and suggestions are rate-limited.
    - **M4 (code).** Deleting or purging a conversation removes its words from `kb_gaps` (migration `20261015090200`). Scheduling retention is still an owner decision (item 20).
    - **Hardening:**
      - One `isSafeSiteLink` check (rejects `//host` and backslashes) for citations, knowledge URLs and every widget link.
      - Only a provider-accepted email counts as "emailed", and stored emails have the resume token removed.
      - The Super Admin rejects non-ASCII signatures cleanly and requires https plus both secrets in production.
      - The visitor-supplied page title is redacted before the model sees it.

    **Accepted, not changed:**
    - Signed admin requests have no nonce. The 5-minute window applies, and the actions are idempotent.
    - Redaction is pattern-based. It cannot catch every name or address, so PRIVACY.md lists this as a residual risk, and the composer asks visitors not to share sensitive details.
    - The cron secret is shared with the enquiry crons.
    - The visitor token lives in `localStorage`, protected by the site CSP.
